# L402 machine commerce (Milestone 4)

R402USD is a demo RGB asset. Human RGB transfers keep their existing wallet policy
and application-controlled approval. Machine purchases use **BTC Lightning sats**,
a separate budget, and the `agent_fetch_resource` tool. They never pay with RGB.

## Start the local demo

Use the existing funded Alice/Bob regtest environment. Preserve its state and the
wallet journals. The six Rust workspace members and original simulated 402 demo
are unchanged; `merchant-server` remains the default simulated merchant binary.

```bash
./scripts/regtest/start.sh
./scripts/regtest/status.sh
cargo build -p merchant-server --bin l402-merchant -p buyer-agent --bin api
npm --prefix apps/wallet-ui ci
npm --prefix apps/wallet-ui run build
set -a
source .var/regtest/wallet.env
source config/l402.env.example
set +a
cargo run -p merchant-server --bin l402-merchant
```

In another terminal, source the same two public configuration files and run:

```bash
cargo run -p buyer-agent --bin api
```

Provide your own `OPENAI_API_KEY` in the server environment, with optional
`AGENT_MODEL` (the existing default is `gpt-5.6-terra`). The existing CLI/API fallback
loader also recognizes the buyer machine-policy variables. No credentials belong
in the frontend, committed environment files, documentation, or screenshots.
`MERCHANT_LIGHTNING_NODE_TOKEN`, if needed, is server-only and must be exported
separately. This local node setup does not require bearer authentication.

Open **http://127.0.0.1:3030**, select Agent, and enter:

> Get the premium report.

`GET http://127.0.0.1:3040/premium/report` costs **3 sats**. The returned BTC/USD
report is explicitly a deterministic fixture, not a current market quote. The
machine receipt shows the cost, policy, authoritative payment status and whether
the resource was actually unlocked. Activity records `machine_purchase`, sats,
resource URL, timestamp, automatic/human approval, hash and node status.

To demonstrate the human boundary, enter:

> Get the extended premium report at http://127.0.0.1:3040/premium/extended.

That endpoint costs **50 sats**. The application pauses at its approval sheet.
Cancel demonstrates the boundary without submitting a second payment. The model
has no approval tool; extra approval fields are rejected. The sheet sends only
the bound plan ID to the existing CSRF-protected application endpoint.

`/public` is free and `/healthz` reports merchant availability. Endpoints and
prices are intentionally fixed for this narrow demonstration.

## Policy and protocol

| Setting | Demo value | Meaning |
| --- | --- | --- |
| `AUTO_APPROVE_MACHINE_BELOW_SATS` | 10 | Inclusive maximum for automatic payment |
| `MAX_MACHINE_PAYMENT_SATS` | 100 | Maximum invoice principal per purchase |
| `MAX_MACHINE_DAILY_SPEND_SATS` | 500 | UTC-day principal budget, including uncertain/failed reservations |
| `ALLOWED_L402_ORIGINS` | `http://127.0.0.1:3040` | Exact origin allowlist |
| `MACHINE_STATE_PATH` | `.var/regtest/machine-state.jsonl` | Durable machine reservations, separate from RGB |

Rust decodes and validates a fixed positive whole-satoshi regtest invoice, rejects
all RGB asset fields, compares the challenge price, checks expiry and available
outbound BTC, then evaluates policy. Execution rechecks the bound invoice, balance
and daily budget. Fees are node-managed and are not included in the principal
budget; the local acceptance payment routed directly with an observed 3-sat debit.
The available figure conservatively uses the largest usable channel's next HTLC
limit, not the total on-chain balance.

The transport follows the [L402 protocol specification](https://docs.lightning.engineering/the-lightning-network/l402/protocol-specification):

```text
WWW-Authenticate: L402 macaroon="<base64>", invoice="<bolt11>"
Authorization: L402 <base64macaroon>:<hexpreimage>
```

A typed 402 JSON body also identifies the resource, amount and invoice. The
merchant uses the `macaroon` crate, a random persisted signing key, version-zero
identifier containing the payment hash and random user ID, and resource/expiry
caveats. Challenges reuse a 10-minute invoice until its final 30 seconds; paid
credentials are reusable for one hour. Verification checks the signature, exact
resource, expiry and SHA256 of the 32-byte payment preimage. Invalid or expired
proof never unlocks a resource. The signing key survives merchant restarts.

Only the payment service constructs execution authority. It calls the existing
node client infrastructure at `/lninvoice`, `/decodelninvoice`, `/sendpayment`,
`/getpayment`, and `/listchannels`. The model sees none of the authorization
material. Preimages are retrieved from authoritative settled node state, verified
against the hash, used in a sensitive header, and never written to the journal.

## Recovery and limits

A locked, mode-0600 journal is flushed before submission. URL and payment hash
identify the existing purchase across process restarts. Once reserved, every
fetch of that URL queries the original payment and retries authentication; it
never buys a new invoice. Transport failure, failed payment, missing proof,
resource timeout and expired credentials do not release a reservation or reset
the budget. A failed journal write fails closed.

The final implementation polls pending status up to 100 times, with 300 ms between
polls (approximately 30 seconds plus node request time). If still pending or
uncertain, it returns that state without claiming purchase. Ask to fetch the same
resource again to recover; never remove its reservation to retry. If paid access
has expired, the tool reports the resource unavailable and does not purchase a
replacement automatically. This is deliberately a one-purchase-per-URL demo, not
subscription or production merchant billing.

Only explicitly configured numeric loopback HTTP origins are supported. Other
hosts, ports, schemes, embedded credentials, queries and fragments are rejected.
Redirects and environment proxies are disabled; response sizes are bounded. This
is a local development profile, not a public HTTP credential deployment.

The agent retains the eight-step tool-loop limit. Its purchased content is treated
as untrusted data. Existing RGB simulation and live-wallet tests remain intact.
The PWA stores neither node credentials nor payment proofs.

## Acceptance and validation

See [the acceptance record](acceptance/l402-purchase.json),
[exact conversation](acceptance/l402-conversation.txt),
[sanitized audit](acceptance/l402-audit.log), and the three `l402-*.png` screenshots.
One real 3-sat payment settled and its proof unlocked HTTP 200. A separate 50-sat
plan stopped at application approval and was cancelled without submission.

The first live attempt used a three-second pending window and needed a follow-up
resource request after settlement. That request reused the same payment. The
window was subsequently extended, with a delayed-settlement regression proving
that a single fetch now waits beyond the former limit and unlocks the resource.
No second live payment was made merely to recheck this timing fix.

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
npm --prefix apps/wallet-ui test
npm --prefix apps/wallet-ui run build
```

HTTP contract tests need local socket access, but no real model key or funded node.
Tests cover free/paid resources, malformed challenges, fixed BTC-only invoices,
automatic and human policy, insufficient balance, failure/pending/uncertainty,
invalid/resource-bound/expired proof, timeout recovery and restarts, duplicates,
URL restrictions, model-forged approval and machine-specific UI rendering.

Validation completed on September 16: **72 Rust tests and 16 frontend tests pass**;
formatting, Clippy with warnings denied, and the production frontend build pass.
The historical live run occurred on September 11. On resuming September 16, node
APIs were initially unavailable; infrastructure restart succeeded, but nodes
remained locked and unlock attempts failed. A new authoritative status query was
therefore unavailable. This does not replace the earlier captured results. No new
invoice was paid, no reservation was deleted, and no reset was performed. Restore
the existing funded environment before attempting another live demonstration.
